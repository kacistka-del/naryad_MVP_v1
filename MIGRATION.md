# Миграция с Base44 на собственный backend

Проект больше не использует платформу Base44 ни для авторизации, ни для данных,
ни для серверных функций, ни для загрузки файлов.

## Что было и что стало

| Было (Base44) | Стало |
|---|---|
| `@base44/sdk` в браузере | `src/lib/self-hosted-db.js` — fetch-клиент к своему API |
| `@base44/vite-plugin` | убран; в `vite.config.js` остался только React + прокси на `/api` |
| `db.auth.*` через платформу | `POST /api/auth/*` с JWT в `localStorage` |
| `db.entities.<Name>.*` | `GET/POST/PATCH/DELETE /api/entities/<Name>` |
| `db.functions.invoke(name)` | `POST /api/functions/<name>` |
| `db.asServiceRole` | не нужен — права проверяет backend |
| `integrations.Core.UploadFile` | `POST /api/uploads` (multipart) |
| `integrations.Core.InvokeLLM` | `POST /api/llm/invoke` |
| `VITE_BASE44_APP_ID`, `VITE_BASE44_APP_BASE_URL` | `VITE_API_BASE_URL` |

## Почему страницы не пришлось переписывать

Каждый модуль брал клиент из `globalThis.__B44_DB__`. Теперь туда подставляется собственный
клиент с такой же поверхностью (`auth`, `entities`, `functions`, `integrations`), поэтому
вся прикладная логика страниц продолжает работать без изменений.

Критично: `src/lib/install-db.js` импортируется в `main.jsx` **самым первым** — до `App.jsx`.
Порядок импортов гарантирует, что глобальный клиент готов до вычисления модулей страниц.

## Модель данных

Сущности из `base44/entities/*.jsonc` переехали в PostgreSQL:

* `users` — отдельная таблица (email, хеш пароля, роль, профиль в `data`);
* `records` — документное хранилище остальных сущностей (`entity` + `data jsonb`).

Такая схема сознательная: она повторяет семантику `filter/get/create/update/delete`,
которую ожидает существующий код страниц, и не требует миграций при добавлении поля.
Поиск по `data` идёт через GIN-индекс. Когда модель устоится, критичные сущности
(`Order`, `Executor`) разумно вынести в типизированные таблицы.

Номера нарядов (`Н-2026-000001`) теперь выдаёт база (`order_number_seq`), а не клиент —
дубликаты невозможны даже при одновременных заказах.

## Права доступа

Раньше фронтенд фактически имел прямой доступ к сущностям. Теперь правила на сервере:

* статус наряда меняется только через `transitionOrderStatus`;
* клиент видит свои наряды и уведомления, админ — все;
* `Category`, `SystemSetting`, `AdminAuditLog` пишет только админ;
* список пользователей и аудит доступны только админу.

## Авторизация

Поток регистрации сохранён полностью, включая подтверждение email кодом из 6 цифр
(`register` → `verifyOtp` → `updateMe`). Вход через Google работает при заполненных
`GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`; без них кнопка вернёт понятную ошибку,
а вход по паролю продолжает работать.

Redirect URI для Google: `https://<ваш-домен>/api/auth/oauth/google/callback`.

## Что осталось в репозитории как справочник

Папка `base44/` больше нигде не используется — она оставлена только как описание
исходных схем сущностей и прежней логики. После сверки её можно удалить целиком.

## Перенос существующих данных

Если в Base44 есть боевые данные, порядок такой:

1. выгрузить каждую сущность в JSON;
2. создать пользователей через `/api/auth/register` или вставкой в `users` с хешем пароля;
3. составить карту старых id → новых uuid;
4. вставить остальные записи в `records`, заменив ссылки (`clientId`, `executorId`, `userId`);
5. выставить `order_number_seq` выше максимального использованного номера.
